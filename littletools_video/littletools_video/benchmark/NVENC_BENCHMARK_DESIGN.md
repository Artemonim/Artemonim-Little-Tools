## NVENC Benchmark — дизайн и целевой пайплайн

Этот документ фиксирует целевую архитектуру и поведение внутреннего NVENC‑бенчмарка в `littletools_video/littletools_video/benchmark`. Он описывает не только текущую реализацию, но и согласованный вектор развития (режимы поиска параметров, метрики, работу с датасетом и API).


## Цели инструмента

- **Локальная калибровка пресетов NVENC** для H.264 и HEVC под конкретную машину (GPU, драйвер, сборка FFmpeg).
- **Сбор объективных метрик качества и эффективности** для разных наборов параметров:
  - скорость кодирования (RTF);
  - размер/битрейт;
  - качество по VMAF/VMAF NEG (при наличии `libvmaf`) или SSIM/PSNR.
- **Генерация отчётов** (CSV/JSON/Markdown) для ручного анализа и для автоматического выбора “золотых” конфигураций.
- **Минимальная внешняя интеграция:** инструмент остаётся внутренним (не попадает в общую CLI LittleTools), но может использоваться как отдельная консольная утилита.


## Состав пайплайна (высокоуровнево)

- **Генерация сетки вариантов** (`generate_variants`):
  - профили: `full`, `extended`, `quick`, `custom`;
  - параметры:
    - `codec`: `h264`, `hevc`;
    - `quality`: текущий фокус — фиксированный CQ (например, 30), но CQ может становиться ещё одной координатой;
    - `b_frames`;
    - `temporal_aq` (TAQ);
    - `rc_lookahead` (RC‑LA);
    - `aq_strength` (AQS);
    - `multipass`: `off` / `fullres` (для VBR HQ);
    - HEVC‑специфические: `b_ref_mode` (`disabled`/`middle`), `main10` (8/10‑бит).
  - в профиль `full` дополнительно включены “якоря”:
    - `anchor-fastest` (минимальное качество, максимальная скорость);
    - `anchor-worst-quality` (специальный HEVC main10‑вариант).
- **Фильтрация сетки** перед запуском бенчмарка:
  - по CQ (`--cq-only`);
  - по кодекам (`--h264`, `--hevc`), при отсутствии обоих флагов — включаются оба;
  - по ограничению `--max-variants` (срез первых N вариантов после фильтрации).
- **Кодирование** (`_encode_once`):
  - построение команды FFmpeg на базе `get_nvenc_video_options` с перезаписью параметров (BF, RC‑LA, AQS, TAQ, BREF, main10, multipass);
  - вывод в `T:\Temp\NVENC` с последующим удалением (если не задан `--keep-outputs`);
  - отключение аудио (`-an`) для ускорения и стабильного расчёта метрик качества.
- **Расчёт метрик качества**:
  - если в FFmpeg доступен `libvmaf`:
    - `VMAF` и `VMAF NEG` через `libvmaf` (JSON‑лог во временный файл, затем парсинг);
  - иначе:
    - SSIM и PSNR отдельными прогонов с парсингом stdout;
  - в обоих случаях бенчмарк остаётся полностью на FFmpeg, без внешних библиотек качества.
- **Расчёт производных метрик**:
  - `size_reduction_percent` — относительное снижение размера;
  - `efficiency_ratio` — отношение `size_reduction_percent` к потере качества по VMAF (используется как вспомогательная метрика, не как единственная цель).
- **Агрегация и отчёты** (`write_reports`):
  - пер‑файловые отчёты: CSV/JSON/Markdown;
  - агрегированные отчёты по вариантам (средние метрики по всем файлам):
    - CSV/JSON, которые можно использовать для последующей авто‑оптимизации;
    - Markdown‑таблица для ручного анализа.
- **CLI и управление пайплайном**:
  - команда `nvenc-benchmark run` (через `python -m littletools_video.benchmark` или установленную консольную команду);
  - параметры запуска (см. раздел “CLI‑интерфейс”);
  - единый **лог консоли** в файл `nvenc_benchmark_YYYYMMDD-HHMMSS.log` в папке `reports` через tee‑обёртку stdout.


## Метрики и целевые критерии

### Основные сырые метрики

- **Пер‑файл (для каждой комбинации параметров и каждого входного видео):**
  - `elapsed_s`: время кодирования;
  - `duration_s`: длительность входного видео;
  - `rtf`: `duration_s / elapsed_s` (real‑time factor);
  - `size_in`, `size_out` и `size_reduction_percent`;
  - `vmaf`, `vmaf_neg` (если доступны);
  - `ssim`, `psnr` (fallback);
  - статус (`ok`, `failed`, `failed-metric`, `software_fallback`) и короткая `note`.

- **Агрегированные по варианту (по всем файлам):**
  - средние `elapsed_s`, `rtf`, `size_reduction_percent`, `vmaf`, `vmaf_neg`, `ssim`, `psnr`, `efficiency_ratio`;
  - количество файлов `count`;
  - параметры варианта (BF, TAQ, RC‑LA, AQS, multipass, BREF, main10);
  - `input_name` (первый входной файл или `(multiple)`).

### Производный критерий `efficiency_ratio`

Текущая реализация рассчитывает:

- `loss = max(0, 100 - VMAF)`;
- `efficiency_ratio = size_reduction_percent / loss` (с отсечкой бесконечностей и больших значений).

Эта метрика полезна как **подсказка** (находить “подозрительно эффективные” варианты), но **не используется как единственная целевая функция** из‑за:

- нестабильности при малом `loss`;
- нелинейной природы шкалы VMAF;
- неявного и сложно интерпретируемого веса “1% размера vs 1 балл VMAF”.


## Цели оптимизации и будущие режимы поиска

### Базовый режим (“grid с ограничением max_variants”)

- Текущий режим `run` интерпретирует сетку как “список вариантов” и просто прогоняет первые `N = max_variants` после фильтрации.
- Это полезно для:
  - ручного анализа;
  - отладки;
  - получения базового датасета для будущей оптимизации.

### Целевая постановка задачи оптимизации

Для “умного” перебора конфигураций планируется использовать следующую постановку (внутри отдельного режима поиска):

- **Основная идея:**  
  минимизировать размер (или битрейт), и/или максимизировать RTF,  
  при мягком ограничении на качество:

  $$[ VMAF_{\text{avg}} \approx T ]$$

  с мягким штрафом за падение ниже T.

- Пример целевой функции для одного trial’а (одной конфигурации параметров):

  ```python
  penalty = max(0.0, target_vmaf - vmaf_avg)
  objective = size_mb_avg + lambda_vmaf * penalty ** 2
  ```

  где:

  - `size_mb_avg` — средний размер по набору клипов;
  - `vmaf_avg` — средний VMAF;
  - `target_vmaf` выбирается адаптивно (см. ниже);
  - `lambda_vmaf` — коэффициент штрафа.

### Выбор порога качества `target_vmaf`

Чтобы не “угадать” порог качества из головы, планируется:

- **Фаза наблюдения** (look‑then‑leap):
  - взять небольшой случайный поднабор конфигураций при фиксированном CQ (например, 30);
  - прогнать их на выбранном наборе клипов;
  - собрать распределение VMAF.
- **Фаза выбора порога:**
  - задать `target_vmaf` относительно наблюдённых значений, например:
    - `T = max(VMAF) − Δ`, где Δ = 2–3;
    - или `T = q`‑ый процентиль (например, 75‑й).
- **Фаза оптимизации:**
  - использовать `target_vmaf` в целевой функции с мягким штрафом, а не как жёсткий hard‑cut.

Такой подход снижает риск “случайно наказать” CQ=30 и позволяет подстраивать порог под реальное поведение VMAF на конкретном контенте.

### Режимы поиска (Roadmap)

- **Random / Monte‑Carlo (`--search random`)**:
  - выбираем N случайных конфигураций из сетки после фильтров по CQ/codec;
  - прогоняем bench, строим Парето‑фронт и анализируем вручную или как вход для более сложной оптимизации.
- **Bayes / TPE (`--search bayes`, с Optuna как optional extra):**
  - используется для “дорогой” оптимизации, когда каждая конфигурация стоит десятки секунд/минут;
  - работает поверх дискретного пространства (категориальные параметры);
  - управляет балансом exploration/exploitation для целевой функции (см. выше);
  - количество trial’ов `n_trials` определяется пользователем:
    - ориентировочно 50–100 trial’ов на усечённом наборе клипов.
- **Гибрид (Random + Bayes + локальный поиск):**
  - стартовая фаза — несколько чисто случайных конфигураций;
  - основная фаза — байесовская оптимизация;
  - финиш — локальный координатный поиск вокруг 2–3 лучших найденных конфигураций (тонкая настройка AQS/RC‑LA/BF).


## Работа с датасетом

### Типы наборов

Пайплайн предполагает два уровня наборов данных:

- **Рабочий набор для обучения/поиска:**
  - несколько коротких роликов (10–60 секунд каждый):
    - NASA‑ролик (3.8 минуты) может резаться на отрывки;
    - 4K‑“витринные” ролики, содержащие много деталей и разных сцен;
  - разнообразие важнее длины.
- **Большой набор для финальной валидации:**
  - полный 3.8‑часовой набор (или другая крупная коллекция);
  - используется только для прогона ограниченного числа финальных конфигураций (например, топ‑3 веса для H.264/HEVC), а не для всех trial’ов.

### Практический сценарий

- Для `--search random` и `--search bayes`:
  - работать на коротком (обучающем) наборе клипов (или отрезков);
  - количество trial’ов выбирать исходя из бюджета времени (часы, а не недели).
- Для подтверждения результатов:
  - взять выбранные конфигурации и прогнать их на полном наборе (несколько часов материала) как отдельную “ночную” задачу;
  - перезаписать отчёты в `reports` для окончательного анализа.


## CLI‑интерфейс (актуальный и планируемый)

### Текущий `run`

```bash
python -m littletools_video.benchmark run \
  --input-dir  littletools_video/littletools_video/benchmark/testData \
  --out        littletools_video/littletools_video/benchmark/reports \
  --profile    full \
  --cq-only    30 \
  --max-variants 200 \
  --require-vmaf \
  --h264        # или --hevc, или оба опустить, чтобы включить оба кодека
```

- **Ключевые флаги:**
  - `--input/--input-dir`: входные файлы или директория с ними;
  - `--out`: папка для отчётов и логов;
  - `--profile`: `full`/`extended`/`quick`/`custom`;
  - `--max-variants`: ограничение количества вариантов после фильтрации;
  - `--require-vmaf`: трактовать отсутствующий VMAF как ошибку;
  - `--vmaf-model-dir`: путь к моделям VMAF/VMAF_NEG (опционально);
  - `--cq-only`: оставить в сетке только заданный CQ (например, 30);
  - `--h264`, `--hevc`: включить H.264 и/или HEVC (если оба флага отсутствуют — включить оба);
  - `--keep-outputs`: не удалять временные файлы из `T:\Temp\NVENC`;
  - `--concurrency`: количество параллельных encode’ов (по умолчанию 1 из‑за GPU).

- **Поведение:**
  - генерирует отчёт per‑file и aggregated (CSV/JSON/MD);
  - пишет лог консоли в `nvenc_benchmark_YYYYMMDD-HHMMSS.log`;
  - live‑строка показывает:
    - files — прогресс по файлам для текущего варианта;
    - vars — прогресс по вариантам;
    - EPF/EPV/EPB/ETAv/ETA.

### Планируемые расширения CLI (search‑режимы)

- `--search random --samples N`:
  - игнорирует `max_variants`, вместо этого выбирает N случайных вариантов из сетки.
- `--search bayes --trials N --target-vmaf T`:
  - включает Optuna (при наличии extra‑зависимости);
  - выполняет N trial’ов, вызывая `run_benchmark` в режиме “одна конфигурация → несколько входов”;
  - возвращает top‑K конфигураций и записывает отдельный отчёт для них.


## Зависимости и packaging

- Базовый режим бенчмарка использует только стандартную библиотеку и уже имеющиеся зависимости LittleTools (Typer, rich, FFmpeg).
- Дополнительные зависимости для `--search bayes` будут оформлены как **опциональный extra**:

  - в `littletools_video/pyproject.toml` планируется добавить:

    ```toml
    [project.optional-dependencies]
    nvenc-bench-opt = ["optuna>=3.0"]
    ```

  - код будет аккуратно проверять наличие Optuna и выводить понятное сообщение, если extra не установлен.


## Итоги

- Бенчмарк остаётся **машинно‑специфичным** инструментом (результаты зависят от GPU, драйверов и ffmpeg‑сборки), но:
  - даёт хорошо обоснованные дефолтные пресеты для данного окружения;
  - может использоваться как внешний инструмент: другие пользователи могут прогнать его на своих машинах и получить “свои” пресеты.
- Дизайн пайплайна учитывает:
  - тяжесть расчёта (VMAF + encode → десятки секунд/минут на trial);
  - необходимость “умных” методов поиска (random/bayes) вместо полного перебора;
  - поддержку подробной отчётности и логов, удобных для дальнейшего анализа.
